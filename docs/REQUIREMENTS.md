# AcIMSWeb 要件定義書

## 1. 文書概要

### 1.1 目的

本書は、AcIMSWeb のパスワード管理機能、画面構成、操作性、セキュリティ、運用に関する要件を定義する。

### 1.2 対象範囲

- ホーム画面
- パスワード管理画面
- パスワード登録・編集画面
- 検索ダイアログ
- 詳細ダイアログ
- 設定画面
- 利用規約画面
- 認証、自動ロック、バックアップ、デプロイ

### 1.3 背景・位置づけ

本システムは、学生時代に開発した C# 版アカウント情報管理システムの後継および移行先として構築する。C# 版は長期間利用してきた一方、現在の開発環境や技術要件に合わせた維持・継続開発が難しくなってきた。そのため、ブラウザで利用できる Ionic + React 版へ移行し、PC とスマートフォンの双方で利用できる構成とする。

また、近年の AI 技術の発達を踏まえ、設計、実装、テスト、ドキュメント作成などの開発工程で AI を補助的に活用する。ただし、生成された設計・コード・文書は開発者が内容を確認し、セキュリティ、動作、保守性の観点から最終的な責任を持って採用する。

本システムは C# 版の単純な再現にとどまらず、既存機能を引き継ぎながら、Web 標準、暗号化、自動ロック、レスポンシブ UI、将来の保守性を考慮した移行先として整備する。

## 2. システム概要

AcIMSWeb は、ブラウザ内にアカウント情報を暗号化して保存するクライアントサイドアプリケーションである。登録データは IndexedDB に保存し、通常のデータ管理処理でサーバーへ送信しない。

## 3. データ要件

### 3.1 パスワード情報

1件の登録情報は、次の項目で構成する。

| 項目 | 必須 | 備考 |
|---|---:|---|
| カテゴリ | 必須 | 登録済みカテゴリから選択可能 |
| アプリサイト名 | 必須 | 管理画面の主な識別名 |
| ID | 任意 | |
| メールアドレス | 任意 | |
| パスワード | 任意 | マスク表示、表示切替、コピー対応 |
| URL | 任意 | 登録時はリンクとして利用可能 |
| 備考 | 任意 | 未入力時は「未登録」を表示せず空欄とする |

### 3.2 保存と保護

- パスワード情報は AES-GCM で暗号化して IndexedDB に保存する。
- マスターパスワードから PBKDF2-SHA-256 で暗号鍵を導出する。
- マスターパスワードそのものは保存しない。
- 復号鍵はアプリ実行中のメモリに保持する。
- データ消去やブラウザデータ消去により情報を失う可能性を明示する。

## 4. 機能要件

### FR-01 初回設定

- 初回起動時はマスターパスワード設定画面を表示する。
- マスターパスワードは4文字以上とする。
- 確認用パスワードと一致しない場合は登録できない。
- 設定完了後にパスワード管理画面を表示する。

### FR-02 認証と画面遷移

- マスターパスワード設定済みの場合、管理画面を開く前に認証を要求する。
- 認証失敗時はエラーを表示し、管理画面を開かない。
- ホーム画面へ戻る操作を提供する。
- 管理画面からホーム画面へ戻る操作を提供する。

### FR-03 パスワード情報の登録・編集・削除

- 新規追加ボタンから登録ダイアログを開ける。
- 情報を保存、編集、削除できる。
- 削除操作は対象データを特定して実行する。
- 詳細画面からも編集・削除できる。
- 登録画面ではパスワードの表示・マスク切替ができる。
- 登録画面では安全なランダムパスワードを生成できる。

### FR-04 検索とカテゴリ絞り込み

- フリーワード検索に対応する。
- 検索対象はカテゴリ、アプリサイト名、ID、メールアドレス、パスワード、URL、備考とする。
- カテゴリによる絞り込みに対応する。
- フリーワードとカテゴリ絞り込みは同時に利用できる。
- 条件をクリアする操作を提供する。
- 検索 UI はスマホ・PC ともに中央のダイアログモーダルで表示する。
- 一覧上の検索バーと検索ダイアログの条件は同期する。

### FR-05 詳細表示

- 一覧の詳細操作から詳細ダイアログを開ける。
- 備考が未入力でも詳細操作を利用できる。
- 詳細画面では、次の項目をコピーできる。
  - カテゴリ
  - アプリサイト名
  - ID
  - メールアドレス
  - パスワード
  - URL
- 備考にはコピー操作を表示しない。
- パスワードは初期状態でマスク表示する。
- パスワードの表示・再マスクを切り替えられる。
- 詳細画面を閉じた場合、パスワードはマスク状態へ戻す。
- コピー成功・失敗を通知する。
- 備考未入力時は空欄で表示する。

### FR-06 表示・省略

- 長い文字列は画面幅と列幅に応じて省略表示する。
- 省略記号は `...` を使用する。
- 表示文字数は固定値ではなく、PC の列幅やスマホのカード幅に合わせて決定する。
- 備考も長文時は省略表示し、詳細画面で全文を確認できる。
- 未入力の備考は「未登録」などの代替文言を表示せず空欄とする。

### FR-07 クイック操作

- 画面右下付近に「↑」「検索」「＋」を縦方向に配置する。
- 上から「↑」「検索」「＋」の順に表示する。
- 「＋」は常時表示する。
- 「↑」は一覧をスクロールした後に表示し、押下すると一覧最上部へ戻る。
- 「検索」は一覧をスクロールした後に表示し、検索ダイアログを開く。
- 3つのボタンは中心線を揃え、「＋」だけ右寄りに見えないようにする。
- PC では画面端から適切な余白を確保する。

### FR-08 PC 管理画面

- PC ではヘッダー付きの管理テーブルを表示する。
- ヘッダー項目はカテゴリ、アプリサイト名、ID、メールアドレス、パスワード、URL、備考、操作とする。
- ヘッダー文字は中央揃えとする。
- 操作欄には詳細、編集、削除を配置する。
- 操作欄のボタンは横並びで、サイズ・高さ・余白を揃える。
- 管理テーブルの列ヘッダーは一覧スクロール時に固定表示する。
- 列ヘッダーはアプリ上部ヘッダーとの間に不要な隙間や重なりを発生させない。
- テーブル幅が画面に収まらない場合は、一覧領域内で横スクロールできるようにする。

### FR-09 スマホ管理画面

- スマホでは1件ごとのカード形式で表示する。
- カードにはアプリサイト名、各データ項目、詳細・編集・削除操作を表示する。
- パスワードはマスク表示を基本とする。
- 各項目のコピー操作を利用できる。
- PC のテーブルと同じデータを表示し、機能差を必要以上に作らない。

### FR-10 設定

- 管理画面から設定ダイアログを開ける。
- JSON 形式でデータをエクスポートできる。
- JSON ファイルをインポートできる。
- インポート時は既存データを置き換えることを確認する。
- 自動ロックの有効・無効と時間を設定できる。
- マスターパスワードを変更できる。
- 対応端末では生体認証を設定できる。
- 設定画面の利用規約リンクは設定コンテンツ内で中央に配置する。

### FR-11 利用規約

- ホーム画面下部に利用規約へのリンクを表示する。
- 設定画面下部にも利用規約へのリンクを表示する。
- 利用規約は共通のモーダル画面で表示する。
- 利用規約モーダルを閉じる操作を提供する。

### FR-12 自動ロックと生体認証

- 指定時間の無操作後に管理画面をロックする。
- ロック後はマスターパスワード認証を要求する。
- 対応するスマホ端末では WebAuthn による生体認証を利用できる。
- PC では生体認証機能を表示・登録・認証の対象外とする。
- アプリを完全に再起動した場合はマスターパスワード認証を必要とする。

## 5. 画面要件

### 5.1 ホーム画面

- アプリの概要を表示する。
- パスワード管理画面を開く導線を表示する。
- 画面下部に利用規約リンクを表示する。

### 5.2 管理画面

- 上部にアプリヘッダー、検索バー、カテゴリ選択を表示する。
- PC では一覧テーブル、スマホではカード一覧を表示する。
- データがない場合は登録を促す空状態を表示する。
- 検索結果がない場合は該当データがないことを表示する。
- ローディング中は読み込み状態を表示する。

### 5.3 モーダル

- 登録・編集、検索、詳細、設定、利用規約をモーダルまたはダイアログで表示する。
- モーダルの内容が多い場合はモーダル内部をスクロールする。
- 検索と詳細は、内容量に合わせたコンパクトなダイアログとする。
- PC・スマホともに操作要素が画面外へはみ出さないこと。

## 6. 非機能要件

### 6.1 対応環境

- Node.js 22 以降で開発・ビルドできること。
- PC とスマホのブラウザで利用できること。
- WebAuthn 利用時は HTTPS などの安全なコンテキストであること。

### 6.2 操作性

- PC とスマホで画面幅に適したレイアウトを表示すること。
- ボタンの意味がアイコンやラベルから判別できること。
- コピー・保存・削除などの操作結果を通知すること。
- 長い文字列が他のボタンや列を押し出さないこと。
- キーボード、タッチ操作のどちらでも主要操作を実行できること。

### 6.3 セキュリティ

- 登録情報を暗号化して保存すること。
- マスターパスワードを平文保存しないこと。
- エクスポート JSON は平文であることを画面・ドキュメントで明示すること。
- 認証前に管理データを表示しないこと。
- コピーや表示解除はユーザー操作によってのみ実行すること。

### 6.4 品質

- TypeScript の型チェックを通過すること。
- 本番ビルドが成功すること。
- 画面遷移と主要認証フローのユニットテストが成功すること。
- PC とスマホの主要画面でレイアウト崩れがないこと。

## 7. 受け入れ条件

1. 初回設定、認証、ホームへの戻りが正常に動作する。
2. パスワード情報を登録、編集、削除できる。
3. PC ではヘッダー付き管理テーブル、スマホではカード表示になる。
4. PC の列ヘッダーがスクロール時に固定され、アプリヘッダーとの間に不自然な隙間がない。
5. 操作欄に詳細、編集、削除が整列して表示される。
6. 詳細画面で備考以外をコピーでき、パスワードをマスク制御できる。
7. 備考未入力でも詳細画面を開け、備考は空欄表示になる。
8. 検索とカテゴリ絞り込みがダイアログで利用できる。
9. 「↑」「検索」「＋」の順に配置され、「＋」は常時表示される。
10. 利用規約へホーム画面と設定画面の両方から遷移できる。
11. JSON エクスポート／インポート、自動ロック、対応端末の生体認証が動作する。
12. `npm run build` と `npx vitest run` が成功する。

## 8. 運用・デプロイ要件

- GitHub Pages 用に静的ファイルを生成できること。
- `package.json` の `homepage` が公開 URL と一致していること。
- `public/manifest.json` のアプリ名、開始 URL、表示形式、アイコン設定を公開環境に合わせること。
- デプロイ前に `npm run lint`、`npm run test.unit`、`npm run build` を実行すること。
- エクスポートデータは平文のため、公開リポジトリや共有フォルダへ保存しないこと。

## 9. 未確定・確認事項

- 利用規約の正式な法務文面、施行日、改訂履歴。
- PC の列幅とブレークポイントの最終値。
